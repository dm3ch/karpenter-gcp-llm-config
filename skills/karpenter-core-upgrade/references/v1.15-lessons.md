## Compilation did not catch all compatibility breaks

The required integration included a `Reboot` method, explicit repair actions/fallbacks and matcher wiring, plus a prediction-store constructor argument. GCP selected replacement repair policies and returned the upstream typed unsupported error for native reboot. That stub did not mean modern replacement repair was unimplemented.

More subtly, `NodeClaimsDisruptedTotal` gained `consolidation_policy` and `termination_mode` labels. The old GCP interruption emission compiled but panicked when exercised. The fix supplied an empty consolidation policy and used core's `nodeclaim.DisruptionTerminationMode` helper. Existing metric assertions exposed the production defect.

**Reusable check:** inspect all provider-owned emissions of changed upstream metrics and test observable emissions, not just constructors/builds.

## Stable defaults can conceal changed behavior

`NodeRepair` stayed disabled by default, yet existing enabled users moved to voluntary repair: applicable `Unhealthy`/all-reason budgets, the Node do-not-repair veto, replacement feasibility and replacement initialization before original deletion. Explicit zero termination grace preserved forceful termination after staging, not all legacy repair semantics. `legacyNodeRepair` offered the old controller as an opt-in escape hatch at that time.

The new `TerminateFirstDrift`, `TerminateFirstRepair` and `PodDeletionCostManagement` alpha gates stayed false. Terminate-first support was partial: dynamic behavior depended on reserved capacity not supported by GCP; static node-limit behavior was separate. Some gate combinations were ignored rather than rejected.

**Reusable check:** document effective behavior for users who already enabled a gate. Audit ordinary settings and prerequisites alongside the gate matrix. Do not restore a historical escape hatch if a future release removed it.

## Optional support needed real provider design

Native reboot and pre-registration CSI attachment-limit predictions were deferred, not silently advertised:

- Native GCE reset involves a hard/non-graceful reset, IAM, replay/idempotency, eligibility and recovery/error handling, not just implementing a method. Tracking: [#681](https://github.com/cloudpilot-ai/karpenter-provider-gcp/issues/681).
- Volume-limit predictions depend on CSI driver, instance family/size and overrides; a universal constant was unjustified. Actual CSINode limits remain important. Tracking: [#682](https://github.com/cloudpilot-ai/karpenter-provider-gcp/issues/682).
- DRA and reserved capacity already had tracking: [#524](https://github.com/cloudpilot-ai/karpenter-provider-gcp/issues/524) and [#239](https://github.com/cloudpilot-ai/karpenter-provider-gcp/issues/239).

These are historical issue links, not assertions about their present status. Recheck existing implementation and issue state before proposing follow-ups or duplicating them.

## Charts, RBAC and migration guidance mattered

The migration added Services read permissions and conditional Pod patch permission for deletion-cost management. No new GCP IAM permissions were needed for the scoped migration. Controller CRDs and both chart distributions changed; operators needed CRD upgrades before new budget reasons, and Helm's controller-chart `crds/` directory does not upgrade existing CRDs automatically.

Metrics changed reason casing/labels, while budget reason casing remained distinct. `consolidateAfter` became optional with a `0s` default. These operator-visible differences belonged in migration guidance, not only generated reference docs.

**Reusable check:** analyze Kubernetes RBAC, cloud IAM, schema defaults and upgrade sequencing separately. Preserve independent migration notes through rebases.

## Keep regression coverage provider-owned and readable

Intermediate versions introduced chart tests, core constructor/matcher tests and a synthetic watch observer. Subsequent user feedback simplified the suite; the merged change removed that scaffolding. The retained policy test directly checks six expected condition/status/toleration policies, replacement actions and explicit zero grace, without relying on policy order or simulating upstream scheduling internals.

Do not copy the initial implementation report as the desired final test architecture. Prefer the current unit-testing skill and the merged diff. Do not remove meaningful regressions solely to make tests shorter.

## Behavioral repair validation needed genuine eligibility

The repair E2E extended one scenario to check budget blocking, do-not-repair veto, and initialized replacement before original deletion admission. Original survival alone would false-pass while replacement-first capacity was still booting; a generic budget event alone did not prove this claim's repair was blocked. Observe the original identity, absence of a replacement during blocking, and deletionTimestamp admission rather than only eventual Deleted events.

Core clamps unhealthy condition transition time to Node creation. Backdating a condition on a fresh Node did not bypass the five-minute toleration, so early negative checks were vacuous and a veto assertion timed out. The fixture was corrected to wait for actual eligibility before asserting blockers.

The original full standard run recorded 49 passes and one COS Stable/GKE minor compatibility failure; a later focused repair run passed on a different SHA. Neither result established a full-standard pass for the final simplified head.

**Reusable check:** respect real eligibility/time semantics, bound negative checks after eligibility, and report exact tested SHAs/environment failures. Each redeploy/rerun needs appropriate explicit live consent; historical consent is not reusable.
